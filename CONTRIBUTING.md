# Contributing

Kori is a personal project, but it's run like a team project, with small reviewed PRs, green CI
and written decisions. These conventions apply to every change, whether a person or an AI
assistant writes it.

## Workflow

1. **Every change starts from a Trello card.** The backlog lives on the private "Kori" board. Each
   task card gives the goal, the scope in and out, acceptance criteria, dependencies and review
   focus.
2. **One card becomes one branch and one PR.** Don't bundle unrelated changes.
3. **Open the PR, pass CI, get it reviewed, squash-merge.** The owner reviews and merges every PR.

## Branches

- `main` is always releasable and protected. Nobody pushes to it directly.
- Work happens on short-lived branches named `<type>/<card-id>-<slug>`, for example
  `feat/m1-05-data-model` or `docs/s2-hosting-adr`.
- The type is one of: `feat`, `fix`, `chore`, `docs`, `ci`, `build`, `refactor`, `test`, `perf`.

## Commit messages

Commits follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <imperative summary, ≤ 72 chars>

<optional body: what and why, wrapped at 72>

Refs: M1-05
```

- **Scopes:** `api`, `web`, `ai`, `infra`, `ci`, `docs`. Leave the scope out for repo-wide chores.
- **Examples:**
  - `feat(api): add session authentication`
  - `fix(web): keep month filter on refresh`
  - `docs: add ADR-0005 hosting`
- **Breaking changes:** add `!` after the type or scope, plus a `BREAKING CHANGE:` footer.
- Because PRs are squash-merged, **the PR title becomes the commit on `main`**, so it must follow
  the same format.

## Pull requests

- **One concern per PR, roughly 300 changed lines at most.**
  - Lockfiles, generated code (`openapi.json`, API clients), autogenerated migration boilerplate
    and vendored UI components don't count.
  - If a PR must be bigger, explain why in its description.
- **Use the PR template.** It asks for What/Why, How to review, Testing, Screenshots (for web
  changes), and a `Refs: <card-id>` line with the card link.
- **Add one review-depth label** so the reviewer can budget time:

  | Label | Meaning |
  |---|---|
  | `review:skim` | About 10 minutes: config, docs, generated code |
  | `review:read` | About 20 minutes: normal feature code |
  | `review:scrutinize` | 30–45 minutes: data model, auth, security, deploy, money handling |

- **CI must be green before review.** Red PRs don't get reviewed.
- **Squash merge only.** The branch is deleted after merge.

## Definition of Done (per PR)

- [ ] Every acceptance criterion on the card is met and ticked.
- [ ] CI is green: lint, format, types, tests, build.
- [ ] Tests were added or updated for the change.
- [ ] Docs or an ADR were updated if a decision or behaviour changed.
- [ ] The PR is linked on the card, and the card is in **In Review**.
- [ ] Review comments are resolved, the PR is squash-merged, and the card is moved to **Done**.

## Testing expectations

These apply as the code arrives.

- **API:**
  - pytest runs against **real Postgres**, never SQLite.
  - Each test runs in a rolled-back transaction.
  - Every endpoint has an **auth test** (401 without a session) and an **isolation test** (another
    user's data returns 404).
- **Migrations:** `alembic check` in CI fails on drift between models and migrations.
- **Web:** Vitest, React Testing Library and MSW. Test behaviour, not snapshots.
- **Coverage:** the API stays at 85% or above.
- **E2E:** Playwright smoke tests, starting in M2.

## Decisions and ADRs

- Significant or hard-to-reverse decisions get an ADR in [`docs/adr/`](docs/adr/README.md).
- To change a decision, write a new ADR that supersedes the old one. Accepted ADRs aren't
  rewritten.

## Local setup

```bash
pipx install pre-commit   # or: pip install pre-commit
pre-commit install        # run the hooks on every commit
pre-commit run --all-files
```

Web setup (Node 22 and pnpm 10, for example via `corepack enable`):

```bash
make web-install   # pnpm install --frozen-lockfile
make web-dev       # Vite dev server; /api is proxied to http://localhost:8000
make openapi       # re-export openapi.json and regenerate the typed API client
```

Commit `openapi.json` and `apps/web/src/api/schema.d.ts` together with any API change. CI
regenerates both and fails on drift.

Language-specific setup for Docker Compose is added to this section by the PRs that introduce it.

## Repository settings (owner checklist)

Apply these once in GitHub → **Settings**:

- **General → Default branch:** rename it to `main` if GitHub created it as `master`. GitHub
  retargets open PRs and redirects old links.
- **General → Pull Requests:**
  - allow **squash merging** only
  - set the default commit message to **"Pull request title"**
  - enable **Automatically delete head branches**
- **Rules → Rulesets**, a new branch ruleset targeting `main`:
  - require a pull request before merging, with 0 required approvals (it's a solo project, and
    PRs are opened under the owner's account)
  - require status checks to pass: `pre-commit` now; add `api-ci`, `web-ci` and `build-image` as
    they arrive
  - require linear history
  - block force pushes and deletions
- **Code security:**
  - enable **Secret scanning** and **Push protection**
  - enable **Dependabot alerts** and **security updates**
- **Actions → General:** set workflow permissions to **Read repository contents**.
- **Labels:** create `review:skim` (green), `review:read` (yellow) and `review:scrutinize` (red).
